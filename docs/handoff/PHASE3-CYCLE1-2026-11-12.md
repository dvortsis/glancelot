## Hot-file grants for this cycle

- **`ui/Main.qml`:** thin call sites only. Each slice may add one component instance or `Loader` for its own surface, and nothing else. B9, E5 and D1 (a tier label overlay, if one is needed) each add one; B8, D2, E6, F3 and REL-01 add none. Commands are handled in the owning component's `Connections { target: viewer }` (EN-07 rule in AGENTS.md "Hot files"). A lazily loaded owner is handled on its `Loader`, as `export-selection` is.
- **`src/app/viewer_controller.{cpp,hpp}`:** each slice adds a library class under `src/app/` and at most a thin call site: one member, one construction line and one `Q_PROPERTY` or `Q_INVOKABLE` forwarder per surface. D1 owns the decode request and result region, E1 the budget construction, D2 one capability property, B9 one restore invokable, and B8 the open-request entry point. The lead resolves include and instantiation conflicts at integration.
- **`ui/SettingsDialog.qml`:** one page registration line each for D2, B8 and E5, with the page in a new file. Nothing else in the file.
- **`ui/MetadataHud.qml`:** D2 owns the status rows. F3 adds one action row through its own component.
- **Root `CMakeLists.txt` and `cmake/`:** each slice may create `cmake/<Slice>Tests.cmake` and add one `include(...)` line for it, as B1 did. REL-01 also owns its provenance block. New sources go in the existing per-area source lists (`cmake/ViewerSources.cmake` and similar), one block per slice, marked with the slice's ID.
- **`src/app/command_registry.cpp`:** one per-slice block, marked with the slice's ID.
- **`translations/glancelot_en_XA.ts`:** regenerate it in your PR if your strings change (`translation_coverage` tests read it). Never hand-merge it. On a conflict, the lead regenerates it at integration.
- **`docs/WORK-QUEUE.yaml`:** your own row only (`guard` enforces this).
- **Never:** `.github/workflows/*`, `scripts/ci/*`, `scripts/lead-*`, `AGENTS.md`, another slice's files, or another session's branch.

## Integration order (serial gate)

The open work lands first: PR 22, the B1 stack (PRs 13, 14 and 16), PR 7, then PR 12. Each cycle slice is then batched as it reaches APPROVED, two to four approved PRs per `lead/integrate-<n>`, one full gate at a time. Expected first batches:
- REL-01 with F3 and E6;
- D2 with B9;
- the E5 PRs;
- D1a with E1a;
- then the second parts of D1, E1 and B8.

The lead merges `main` into a reviewed branch that keeps falling behind (the landing lane).

## Every slice's handoff

`docs/handoff/<SLICE>-HANDOFF.md` follows the AGENTS.md pre-handoff checklist:
- fail-before evidence;
- the grant check against this document;
- the exact base;
- the full offscreen `ctest` output from the cloud build;
- "Decisions taken" and "Open questions for the lead".

It also says whether the ui-design-skills were available. Commits follow Conventional Commits with a `Task: <SLICE>` trailer. The cloud has no commit hook, so run `python scripts/ci/commit_lint.py --range origin/main..HEAD` and `python scripts/ci/pr_guard.py --base origin/main --head-ref <branch>` before each push.
