# F071 feasibility: lightweight image conversion, resize and export presets

EN-09 (track session S4, Phase 0 cycle 1). Base `afeac1a`. Written 2026-10-22. A proposal for the lead: nothing here is a support claim or delivery evidence.

**Recommendation: GO** for a Qt-only JPEG/PNG/WebP(/TIFF) slice built as a sibling of the D8 export family, with an explicit "ICC preserved, all other metadata removed" policy that the export **enforces** by handing the writer a freshly built `QImage` with an empty text map (Qt's readers and writers otherwise carry JPEG comments and PNG tEXt/zTXt/iTXt chunks, including XMP, from source to output; section 2); **DEFER** AVIF and JPEG XL encoding, and **DEFER** high-quality Lanczos3 resampling until VIEW-05's resampler exists so both share one implementation. Size L. Depends on: D1 DECODE-TIER, D8 (F046/F032 export worker family), E1 RESOURCE-LEDGER; EN-02 for WebP in the container.

## 1. What the feature needs in this codebase

Inventory row F071: "Lightweight image conversion/resize/export presets | C / P2 / L | Qualified encoders/export service; preview dimensions, color/metadata/quality policy, output conflicts and cancellation; never default to overwriting originals."

Sibling rows it must share machinery with, not duplicate:

- F046 "Privacy-aware derived export with optional GPS/metadata stripping | N / P2 / L | Export worker, metadata schemas; clear preserved/removed fields, filename/output policy, verify exported bytes and retain originals."
- F032 "Contact sheet export with filenames and chosen metadata | N / P2 / L | Bounded export worker; preview pagination, output dimensions/quality and overwrite policy; export never alters source media."
- F070 "Selection manifest or CSV export | N / P2 / M" - already delivered as `selection_export`, and the pattern to copy.

**F046 / D8 inherit the same metadata trap.** Any derived export that decodes with `QImageReader` and encodes with `QImageWriter` carries the source's JPEG comments and PNG text chunks (including an XMP packet that can hold GPS) into the output unless the text map is cleared (section 2). D8's privacy-aware export must use the same clearing step and the same per-format allowlist test as F071 (section 5), extending the allowlist only for fields it deliberately preserves (for example a future EXIF writer adds APP1 EXIF with a field-level allowlist inside it); one shared helper in the export worker family should do it for all three consumers.

There is **no requirement row** for F071 in `docs/REQUIREMENTS.md`; the nearest related row is VIEW-05 "Lanczos3, bicubic, Mitchell and area downsampling | M3 default; M5 alternatives". So F071 is an inventory proposal and the lead would add acceptance criteria through change control.

### What to reuse (this is most of the design)

**OPERATION-JOURNAL (B2) is not a prerequisite**, and that is worth stating plainly: export creates new files and never mutates a source, so there is nothing to undo on the originals. The one exception is an explicit `overwrite` of a *previous export's* output, which should be refused by default and, if ever allowed, treated like any other destructive write.

New components:

- `include/glancelot/image_export.hpp` (a new contract, lead-frozen) - `ImageExportRequest{generation, items, destinationFolder, naming, format, quality, resize, colorPolicy, metadataPolicy, collision, revalidate, maxItems}` and a result mirroring `ExportResult`. Deliberately the same shape as `selection_export.hpp` so the two read alike.
- `src/core/image_export.cpp` - orchestration only: no decoding, no encoding of its own.
- Encode in the worker process. The decoder worker already owns every image parser; extend it with an `--encode` request (source path or an already-decoded shared-memory buffer in, destination temp path out) so neither decode nor encode ever runs in the GUI process. The parent keeps the rename, the collision policy and the ledger.
- A preset model plus the export dialog (preview dimensions, estimated output size, the metadata policy statement).

Owner: **Track D**, as a sibling packet of **D8** ("F046 + F032 export + F045 AI metadata"). D8 already builds the export worker family; F071 should be the third consumer of it, not a fourth implementation.

"Write our own encoder" is a non-starter and is listed only to dismiss it: Qt already bundles mature encoders, and hand-writing a JPEG or PNG encoder would add risk for no benefit. ### What Qt 6.8's readers and writers actually do (checked in the v6.8.3 sources)

| Format | Quality / options | ICC profile | EXIF / XMP | `QImage` text (comments, text chunks) | Other tags written |
| --- | --- | --- | --- | --- | --- |
| JPEG | `quality` 0-100 (default 75), `optimize` (`optimize_coding`), `progressive` | **Written** as APP2 chunks from `image.colorSpace().iccProfile()`, split across markers [7] | **Not written.** EXIF (APP1) is only *read*, to recover orientation; APP1 XMP is neither read nor written [7] | **Read and written.** The reader saves COM markers (`jpeg_save_markers(&info, JPEG_COM, 0xFFFF)`) and calls `setText` for each; the writer's `set_text` emits one COM marker per key from `qt_getImageText(image, description)`, truncated to 65533 bytes [7][11] | APP0 JFIF (libjpeg's `jpeg_set_defaults` enables it for RGB and grayscale and Qt never turns it off) with a density always filled from dots-per-metre; APP14 Adobe for CMYK output [7] |
| PNG | `CompressionRatio` -> `png_set_compression_level` | **Written** as `iCCP`, named from `QColorSpace::description()` [8] | no eXIf handling; XMP lives in the `XML:com.adobe.xmp` iTXt chunk, which is ordinary text to Qt (next column) | **Read and written.** `readPngTexts` collects tEXt/zTXt/iTXt via `png_get_text` (iTXt as UTF-8) and `readPngImage` calls `setText`; `set_text` writes every key with `png_set_text`, as iTXt when a value has characters above U+00FF or control characters, compressed (zTXt or compressed iTXt) when the value is 40 characters or longer [8][11] | `pHYs` whenever dots-per-metre is positive (always, in practice); `oFFs` only for a non-zero `QImage::offset()`; `gAMA` only if a writer gamma is set and no ICC is written; `PLTE`/`tRNS` for palette images; never sRGB, cHRM, tIME, sBIT or bKGD [8] |
| WebP | `quality` < 100 -> lossy at that quality; `quality` == 100 -> **lossless** with effort 70 | **Written** via the WebP mux ICC chunk [9] | not read, not written (VP8X flags "no XMP, EXIF") [9] | not used [9] | none |
| TIFF | compression option; writes `Grayscale16`, `RGBX64`/`RGBA64`, and the 16/32-bit float formats | **Written** as `TIFFTAG_ICCPROFILE` when the colour space has an ICC profile [12] | not read, not written; no ImageDescription or XMLPacket handling [12] | not used [12] | `TIFFTAG_ORIENTATION` from the writer's transformation (1 by default), resolution [12] |

The text survives every processing step an export would use. `QImage`'s `copyMetadata` copies the text map (`dst->text = src->text`) along with DPI, offset and colour space, and it is called by `convertToFormat`, `copy`, `transformed` (and therefore `scaled`, `scaledToWidth`, `scaledToHeight`), `smoothScaled`, `mirrored`, `rotated90/180/270` and `colorTransformed`; the in-place `convertToColorSpace` the worker uses keeps the image's own metadata [11]. `qt_getImageText` starts from the `QImageWriter` description (`setText`/`setDescription`) and adds every non-empty `QImage` text key not already present [11].

So the brief's assumption needs two corrections: **`QImageWriter` drops EXIF and preserves ICC**, for JPEG, PNG and WebP alike, provided the `QImage` handed to it carries a colour space; **but it also writes back whatever text the reader found**. A PNG exported by Lightroom or darktable carries its XMP (which can include GPS, creator and keywords) in an iTXt chunk; re-encoded as PNG it keeps that XMP, and re-encoded as JPEG the XMP becomes a JPEG comment. Source JPEG comments pass through the same way. "EXIF removed" is therefore not the same as "metadata removed", and the policy has to clear the text explicitly:

- **Recommended v1 policy:** bake orientation (the decoder already applies `setAutoTransform(true)`, so pixels arrive upright and an orientation tag would double-rotate), preserve the colour profile by tagging the output, **clear everything else before writing**, and **state in the UI that all other metadata is removed** - EXIF, GPS, XMP, comments, text chunks and maker notes. That is honest, it is the privacy-safe default F046 wants, and it needs no EXIF writer.
- **How to clear.** Qt 6.8 has no public call that removes a text key: `QImage::setText(key, QString())` stores an empty value, and the writers still emit the key [11]. So D9a must not try to strip keys from the decoded image. The encode step builds the output from pixels only: a new `QImage` of the same size and format whose scanlines are copied from the processed image (for example wrapping `constBits()`/`bytesPerLine()` in a new `QImage` and calling `.copy()` on that wrapper), then sets the colour space (when the colour policy keeps it) and the DPI. **DPI is always written** (JFIF density, PNG `pHYs`, TIFF resolution), because a new `QImage` has Qt's default non-zero dots-per-metre; so D9a sets it explicitly from the preset (default 72 dpi) to make the output deterministic and to make clear the value is not the source's. **Colour tables:** `copyMetadata` does not copy the colour table and a wrapper over external data starts with none, so an `Indexed8` or `Mono` image rebuilt this way would encode without its palette. The v1 rule is to **convert first**: before the rebuild, any image with a colour table is converted to `Format_Grayscale8` if every entry is grey, otherwise to `Format_RGB32` or `Format_ARGB32` (alpha kept); the rebuild accepts only formats with no colour table and asserts `colorCount() == 0`. Palette-preserving output is a possible later preset, not v1. It must assert `textKeys().isEmpty()` before `QImageWriter::write`, must never call `QImageWriter::setText` or `setDescription`, and must not rely on defaults. The rule applies to both worker encode inputs: a re-decode from the source path carries the reader's text through every conversion, and a shared-memory pixel buffer arrives without text but also without a colour space, so the colour space must be passed explicitly in the request.
- Preserving selected EXIF fields means writing our own APP1 block (we already have a bounded EXIF *reader* in `src/app/metadata_parser.cpp` with a 256 KiB read cap, so the structure is understood) - that is F046's "clear preserved/removed fields" work, and it should land in D8, not here.

### Resampling quality

`QImage::scaled(..., Qt::SmoothTransformation)` uses Qt's `qimagescale`, an Imlib2-derived smooth scaler (the file is licensed BSD-2-Clause AND Imlib2, with SSE4.1 paths) [10]. It is a reasonable area/bilinear-class filter and it supports the 16-bit and float formats, but it is **not** Lanczos3, so it is not what VIEW-05 promises ("Lanczos3, bicubic, Mitchell and area downsampling"). Two honest options:

1. **v1:** use `Qt::SmoothTransformation`, label the preset's resampler by name in the UI, and do not claim Lanczos. Also pre-scale in halves for very large reductions (repeated 2:1 box steps down to within 2x of the target, then one smooth step) to avoid aliasing on big minifications.
2. **Later:** when VIEW-05's resampler lands in Track D, reuse it for export so the exported pixels match what the canvas showed. That is the right long-term answer and another reason not to write a private Lanczos here.

## 3. Platform capability

- **Windows**: fully supported with no new dependency. `qtimageformats` is already in the Windows dev tree, so WebP and TIFF presets work. No change to `scripts/build.ps1 -Package` and no new notices.
- **Native Linux**: same, where `qtimageformats` is present. JPEG and PNG are in qtbase and always available.
- **Docker/noVNC**: works, with two real limits the UI must state rather than discover at write time.
  1. `/photos` is bind-mounted **read-only** in `compose.yaml`. An export therefore cannot be written next to the source. The only writable location is the named `/config` volume. The destination picker must default there in the container and must refuse `/photos` with a clear reason, not an I/O error.
  2. There is **no download path**. `docker/start.py` runs Xtigervnc, openbox, the viewer and websockify; browser upload/drop is not implemented and neither is a file download (`docs/DOCKER.md`). So a container user can produce files inside `/config` but cannot fetch them through noVNC. That makes F071 in the container useful only to someone who can reach the volume by other means, and the docs must say so.
  3. `qtimageformats` is absent until EN-02, so only JPEG and PNG presets exist there; the capability model (D2) must report that rather than silently omitting formats from the preset list.
- All clients share one desktop and one cursor in the container, so a long export must not block the single session - the existing queue-and-progress pattern covers this.

## 4. Security model

- **Untrusted input stays behind the existing boundary.** Decode happens in `glancelot-decoder`; encode should too. Nothing in the GUI process parses or writes image bytes.
- **Never overwrite originals, by construction, not by policy.** Reuse `selection_export`'s two hard rules: the destination can never resolve to a selected/source item (`DestinationIsItem` must be refused *even when* `overwrite` is set), and the write goes to a temporary sibling that is renamed into place, so a crash or cancel leaves neither a partial output nor a damaged original. Default collision policy `Skip` or `RenameBoth`, never `Overwrite`.
- **Revalidate source identity** before each encode (`FileIdentity` + revision), because a batch export is long-running; the worker already probes the source revision before and after decoding and fails with "Source revision changed while decoding" - keep that and surface it as a per-item skip rather than a batch failure.
- **Bound everything**: items per request (`maxItems`), decoded bytes per item through the ledger, output pixel dimensions (a resize preset must not be allowed to request 100000 x 100000), and the number of concurrent encodes. A 32768 x 32768 source at 4 bytes per pixel is already 4 GiB of RGBA, far above the 256 MiB decode ceiling, so the preset UI must show the estimate and the engine must refuse rather than try.
- **Disk-full and permission errors** must produce `Failed` with the real reason and leave no temporary file; test with a deliberately tiny filesystem or a write-protected destination.
- **Output naming is attacker-adjacent too**: names derived from source filenames must go through `MutationService::validateTargetName`, must not inherit control characters or trailing dots/spaces (Windows), and must not be allowed to collide case-insensitively on Windows while looking distinct.
- **Metadata removal is a privacy feature**: if the UI says metadata is removed, the output must be built without the source's text map (section 2) and a test must verify the output bytes structurally against a **per-format allowlist**: every marker, chunk or tag in the output must be one the Qt 6.8.3 writer is known to emit for that output and policy (section 5), and **anything else fails**, including containers no one has thought of yet (APP13 IPTC, APP11 JUMBF/C2PA, a PNG private chunk, an unknown RIFF chunk, a TIFF Make or Artist tag). A deny-list of known containers would pass the next leak (a later EXIF writer in D8, a Qt upgrade, or qtimageformats acting on its own "consider parsing EXIF and/or XMP" note). F046's "verify exported bytes" criterion applies here too, and D8 must reuse the same clearing helper and the same allowlist test.

## 5. Test strategy

Generated media only, nothing committed:

- Sources painted with `QPainter` and written in-test: PNG with alpha, JPEG, 16-bit TIFF, an image with a non-sRGB colour space attached, an image with an EXIF orientation tag (write the APP1 block by hand, as the project's own EXIF tests already imply is possible), a 1x1 image, and an extremely wide 1 x 20000 image.
- **Metadata-carrying sources** (generated with Qt itself, which writes them through the paths described in section 2): a PNG whose `XML:com.adobe.xmp` text value is an XMP packet with a GPS property (`exif:GPSLatitude`) and at least one character above U+00FF, so Qt writes it as a compressed iTXt chunk; a PNG with two further keys, one with a plain Latin-1 value under 40 characters (written as tEXt) and one with a plain Latin-1 value of 40 characters or more (written as zTXt); a JPEG carrying a COM marker (via `QImage::setText` before writing), a hand-written APP1 EXIF block with GPS tags, a hand-written APP1 XMP packet and an APP13 IPTC block; a WebP with hand-inserted `EXIF` and `XMP ` RIFF chunks (VP8X flags set); a TIFF with hand-written ImageDescription, Make and Artist tags; and an `Indexed8` PNG (to exercise the convert-first rule). The WebP and TIFF sources guard against Qt starting to read those containers in a later version. Check the fixtures themselves first (the chunks and markers are present), so the test cannot pass on an empty fixture.
- **Round-trip and policy assertions**: JPEG output at quality 50 and 95 (assert size ordering and that both decode); PNG output preserves alpha exactly; WebP at quality 100 is lossless (decode and compare pixels exactly); output carries an ICC profile when the source had one; orientation is baked (pixels match the upright source).
- **Metadata assertions: a per-format allowlist, checked by walking the structure, not by substring search**, for every metadata-carrying source and every output format. Each walker lists every block it finds and **fails on anything not in the allowlist**. The allowlists are exactly what the Qt 6.8.3 writers can emit for the v1 policy (sources [7][8][9][12]); "colour kept" means the colour policy preserves the profile (the v1 default).

  If a later preset adds a writer option that emits further structural blocks (a TIFF compression mode with its own tags, a JPEG restart interval), the allowlist is extended in that packet with each block named, never relaxed to "anything structural". The forbidden items in the right-hand column stay as **named assertions** on top of the allowlist, so a failure says what leaked (for example "APP1 XMP present"), not only "unexpected marker 0xFFE1". Also assert, inside the encode step, that the `QImage` passed to `QImageWriter::write` has empty `textKeys()` and `colorCount() == 0`. A JPEG output from the PNG-with-XMP source must contain no COM marker (the specific leak in section 2).
- **Resize**: target dimensions honoured exactly, aspect ratio preserved when asked, a large minification produces no aliasing worse than a reference (compare against an independently computed box average within a tolerance), and the resampler name in the result matches what was requested.
- **Collision and safety**: destination exists -> `DestinationExists` with default policy and nothing written; destination resolves to the source item -> refused even with `overwrite` true, and the source's bytes are hash-identical afterwards; `RenameBoth` produces a deterministic, validated name.
- **Failure and cancellation**: `stop_token` mid-batch (completed items remain, the in-flight item leaves no temporary file, the result is `Cancelled`); worker killed mid-encode; destination folder read-only; destination full; source deleted or modified between snapshot and encode (`Missing`/`Changed` skip); a result whose generation is stale is dropped.
- **Container case**: an export targeting `/photos` is refused with a named reason rather than failing on `EROFS`.
- New test file `tests/image_export_ui_tests.cpp` plus a core target in a lead-provided `cmake/ImageExportTests.cmake`; never added to `tests/grid_ui_tests.cpp`. Note that export tests write real files, so they must use a per-test temporary directory and clean up, and `ThumbnailService::shutdown()`'s precedent applies - stop workers before destroying temporary media.

**Stays unverified / RUNBOOK:** perceptual quality judgements ("does quality 85 look right"), throughput on real hardware and network shares, and whether a given third-party tool accepts our outputs. Also unverified until EN-02: WebP and TIFF presets in the container.

## 7. Recommendation and what would change it

**GO**, for a Qt-only slice: JPEG and PNG first, WebP and TIFF behind the capability model, resize via Qt's smooth scaler with its name shown, ICC preserved, all other metadata (including the comments and text chunks Qt would otherwise carry through) removed, tested against a per-format allowlist of what the writer may emit and *said* to be removed, and every write going through the `selection_export` safety pattern. This adds no dependency, no notice, no packaging change and no journal requirement, and it reuses three pieces of machinery the project already has.

**DEFER AVIF and JPEG XL encoding.** libavif is BSD-2-Clause [3] and libjxl BSD-3-Clause [5], so licence is not the obstacle; the obstacle is that AVIF encoding means adopting an AV1 encoder (aom, SVT-AV1 or rav1e), which would be the largest dependency in the project by a wide margin, and libjxl is still pre-1.0 at v0.12.0 [6]. Both also belong to the FMT-04 decode decision in `docs/DEP-DECISIONS.md`; export should follow that decision rather than force it.

**DEFER Lanczos3.** Promote it when VIEW-05's resampler lands in Track D, then reuse that code so exported pixels match displayed pixels. Writing a second resampler here would guarantee they disagree.

**Do not use libwebp directly.** Qt already bundles it and `QImageWriter`'s WebP path exposes both lossy quality and lossless [9]; a direct dependency would duplicate a library we already ship.

What would change this:

1. If the lead will not accept "all metadata except ICC removed" as the v1 default, F071 must wait for F046's metadata-preservation work, because a correct EXIF writer is a real piece of work and belongs there. That makes F071 **DEFER until D8 is integrated** rather than GO alongside it.
2. If a requirement row is added demanding byte-exact Lanczos3 output parity with the canvas, sequence F071 after VIEW-05's M5 alternatives.
3. If the container becomes a primary export target, F071 needs a download path out of noVNC first - that is F074/F076-family work, not this packet, and without it the container story stays "writes to `/config`, retrieve it yourself".

7. Qt 6.8.3 JPEG handler - `quality` (default 75), `optimize_coding`, `progressive`; writes the ICC profile as APP2 markers from `image.colorSpace().iccProfile()`; reads EXIF only to recover orientation and writes none; picks `JCS_GRAYSCALE`, `JCS_RGB` or `JCS_CMYK` before `jpeg_set_defaults` (so libjpeg's default JFIF APP0, or Adobe APP14 for CMYK, is written) and never changes `write_JFIF_header`; fills `density_unit`/`X_density`/`Y_density` from dots-per-metre; sets no restart interval; writes the ICC APP2 only for RGB or CMYK; `readJpegHeader` calls `jpeg_save_markers(&info, JPEG_COM, 0xFFFF)` and `QJpegHandlerPrivate::read` calls `image->setText(...)` for each comment; `set_text` writes `jpeg_write_marker(cinfo, JPEG_COM, ...)` for each key from `qt_getImageText`, truncating at `maxMarkerSize = 65533` - https://raw.githubusercontent.com/qt/qtbase/v6.8.3/src/plugins/imageformats/jpeg/qjpeghandler.cpp
8. Qt 6.8.3 PNG handler - writes `iCCP` from the image colour space; `readPngTexts` reads tEXt/zTXt/iTXt with `png_get_text` (iTXt via `QString::fromUtf8`) and `readPngImage` calls `outImage->setText(...)`; `set_text` writes every key from `qt_getImageText` with `png_set_text`, iTXt for characters above U+00FF or control characters, compressed when `it.value().size() >= 40`; no eXIf handling; other chunks written: IHDR, iCCP (valid colour space with a profile), gAMA (writer gamma set and no iCCP), PLTE/tRNS (palette), oFFs (non-zero offset), pHYs (positive dots-per-metre); no sRGB, cHRM, tIME, sBIT or bKGD; gIFg/gIFx only through animation setters `QPngHandler::write` never calls; supports `CompressionRatio` - https://raw.githubusercontent.com/qt/qtbase/v6.8.3/src/gui/image/qpnghandler.cpp
9. Qt 6.8 WebP handler - quality < 100 is lossy at that quality, quality == 100 switches to lossless with effort 70; writes the ICC profile; reads and writes no EXIF, XMP or `QImage` text ("Has ICCP chunk, no XMP, EXIF or animation") - https://raw.githubusercontent.com/qt/qtimageformats/6.8/src/plugins/imageformats/webp/qwebphandler.cpp
10. Qt 6.8 `qimagescale.cpp` - Imlib2-derived smooth scaler, "SPDX-License-Identifier: BSD-2-Clause AND Imlib2", with SSE4.1 paths; this is what `Qt::SmoothTransformation` uses, and it is not Lanczos - https://raw.githubusercontent.com/qt/qtbase/6.8/src/gui/painting/qimagescale.cpp
11. Qt 6.8.3 `qimage.cpp` - `copyMetadata` copies physical metadata, `dst->text = src->text`, offset and colour space; called from `copy`, `convertToFormat_helper`, `transformed` (which `scaled` calls), `smoothScaled`, `mirrored_helper`, `rgbSwapped_helper`, `rotated90/180/270` and `colorTransformed`; `setText` is `d->text.insert(key, value)` (no removal); `qt_getImageText` starts from `qt_getImageTextFromDescription(description)` and inserts every non-empty `image.textKeys()` key not already present - https://raw.githubusercontent.com/qt/qtbase/v6.8.3/src/gui/image/qimage.cpp
12. Qt 6.8.3 TIFF handler - reads and writes `TIFFTAG_ICCPROFILE`; `QTiffHandler::write` sets IMAGEWIDTH, IMAGELENGTH, PLANARCONFIG, RESOLUTIONUNIT, XRESOLUTION, YRESOLUTION, ORIENTATION (from the writer transformation), ICCPROFILE (non-empty profile only) and, per format, PHOTOMETRIC, COMPRESSION, BITSPERSAMPLE, SAMPLESPERPIXEL, SAMPLEFORMAT, ROWSPERSTRIP, COLORMAP, EXTRASAMPLES, INKSET; one directory, no SubIFDs, no SOFTWARE or DATETIME; no `setText`/`text()`, ImageDescription, XMLPacket or EXIF handling - https://raw.githubusercontent.com/qt/qtimageformats/v6.8.3/src/plugins/imageformats/tiff/qtiffhandler.cpp
